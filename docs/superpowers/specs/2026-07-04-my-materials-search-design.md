# 我的资料搜索增强版设计稿

日期：2026-07-04
阶段：产品设计评审稿
适用范围：资料库 > 我的资料，重点覆盖上传后的资料管理、资料健康度、混合检索与 AI 精排结果展示

## 1. 设计 brief 回放

产品对象是考研 Agent 助手里的“用户上传资料库”。用户上传资料的核心目的不是收藏文件，而是在后续检索时能精确找到自己想要的片段。因此这次优化不优先做花哨管理功能，而是把“上传是否可信、资料是否可用、检索为什么命中、AI 精排如何介入”讲清楚。

现有项目已经具备：

- `materials/` 纵向链路：上传、解析、公式清洗、质量报告、切块、索引、搜索。
- 前端资料库入口：资料库内切换“我的资料 / 系统资料”，我的资料按学科筛选、上传、列表、搜索。
- 搜索后端增强：`mode=hybrid/llm`、自适应召回计划、`llm_rerank`、`retrieval_plan`、搜索结果 metadata。
- 两份真实资料测试：概率统计主册与徐涛思修强化班笔记，`qwen3.6-27b` 精排模式在 48 个测试用例中做到正例 top1 命中、负例不展示，但平均延迟约 8 秒。

本设计稿只讨论“我的资料”的产品体验，不改 `qa/`，不做资料库自然语言助手，不重写整体前端架构。

## 2. 设计目标

P0 目标：

- 用户能明确选择搜索范围：当前学科、当前资料、全部我的资料。
- 用户能明确选择搜索模式：快速检索、AI 精排。
- 搜索结果能说明“为什么展示”：命中方式、资料来源、标题路径、AI 判定、排序原因。
- 明显不相关内容不展示；弱相关内容进入“相关参考”而不是混在强结果里。
- 多概念查询能显示覆盖情况，例如“已覆盖：二项分布、泊松分布；未覆盖：指数分布”。

P1 目标：

- 资料列表显示解析健康度：质量状态、chunk 数、索引状态、最近入库时间。
- 资料详情抽屉把普通用户关心的信息和开发诊断信息分层。
- 上传完成后给出可读的入库结果，而不是只说生成了多少 chunks。

非目标：

- 不把 parse_report、formula_cleaning、chunks 删除；它们是诊断资产，只是不应该默认暴露给普通用户。
- 不把 AI 精排设为唯一搜索方式；它慢且依赖模型额度，应作为显式模式或异步增强。
- 不新增大数据库重构、真实多用户权限、PDF/MinerU 横向扩写。

## 3. 信息架构

保留现有大结构：

```text
左侧一级入口：问答 / 资料库 / 规划 / 院校查询
资料库页内：我的资料 / 系统资料
我的资料页内：上传区 / 学科 tab / 资料列表 / 搜索工作台
```

建议把“我的资料”主区域重排为“常驻两栏 + 按需抽屉”：

```text
左列：资料列表与健康度
中间：搜索工作台与搜索结果
右侧：资料详情或结果详情抽屉，默认不展开
```

原因：用户最常用动作是搜索，搜索应从附属面板升级为主工作台；上传和列表仍存在，但不要压过检索。资料详情是辅助检查面板，应由“详情”或“查看片段”触发，不应该默认长期占用搜索结果宽度。

响应式规则建议：

- 宽屏：资料列表 + 搜索工作台常驻，详情抽屉可同时打开。
- 中等屏：资料列表 + 搜索工作台常驻，详情以右侧覆盖抽屉打开。
- 窄屏：搜索工作台优先，详情进入页面级抽屉或单页视图。

## 4. 上传与入库闭环

上传入口仍保持现有表单：文件、学科、资料类型。

上传完成态需要显示：

- 资料名。
- 学科与资料类型。
- 入库阶段是否完成：解析、公式清洗、质量报告、切块、索引。
- `quality_status` 与 `overall_confidence`。
- chunk 数。
- 是否有可处理警告。

普通用户看到的是：

```text
入库完成
质量：高
已建立索引：181 个片段
可搜索：是
提醒：发现 2 条公式清洗提示，可在详情中查看
```

开发/高级诊断放入详情抽屉：

- `parse_report.json`
- `formula_cleaning`
- `llm_cleaning`
- `pipeline_events.jsonl`
- chunks 预览
- search_index 摘要

结论：`parse_report`、`formula_cleaning`、`chunks` 不多余。它们对普通用户默认收起，对调试检索质量、解释入库问题很重要。

## 5. 搜索工作台

搜索区建议采用一行主搜索 + 一行约束：

```text
[搜索框：方差公式] [搜索]
范围：当前学科 / 当前资料 / 全部我的资料
模式：快速检索 / AI 精排
结果数：最多 6 / 10 / 15
```

默认值建议：

- 范围默认：当前学科。
- 如果用户从某个资料卡进入搜索，默认：当前资料。
- 模式默认：快速检索。
- 当查询包含多个概念、短术语、公式、或快速检索置信度不足时，提示可切换 AI 精排。

资料卡上的按钮行为：

- “在本资料搜索”：不打开新的搜索框，也不打开详情；只把常驻搜索工作台的范围切到当前资料，并聚焦搜索框。
- “详情”：打开右侧资料详情抽屉。
- 搜索结果里的“查看片段”：复用右侧抽屉，但内容切换为结果片段详情。

AI 精排不建议默认自动开启，因为真实测试约 8 秒一次。更好的第一版体验是：

- 用户点“AI 精排”后明确进入慢但更准的模式。
- 搜索状态显示“AI 正在判定结果是否适合展示”。
- 结果卡展示 AI 判定与理由。
- 额度不足或调用失败时明确显示“已回退快速检索”，不能让用户误以为 AI 已经判定。

## 6. 结果展示模型

搜索结果拆成两组：

- 强匹配：LLM `decision=primary`，或 hybrid 高置信直接命中。
- 相关参考：LLM `decision=related`，或 hybrid 中等相关但不是直接答案。

不建议把“方差公式”和“协方差”完全隔离到无法展示。更合理的是：

```text
强匹配：
1. 方差定义与公式
2. 常见分布的方差

相关参考：
1. 协方差
2. 相关系数
```

关键是视觉上必须区分，不让相关扩展抢占强匹配排序。

每张结果卡显示：

- 资料名。
- 标题路径。
- chunk 类型或片段编号。
- 命中方式：关键词、向量、公式、AI 精排。
- AI 判定：强匹配 / 相关参考 / 已过滤。
- 命中理由：短句，不直接暴露大段调试字段。
- 片段预览。
- 操作：查看片段、定位资料、复制引用、设为当前资料搜索。

## 7. 多概念查询

多概念不需要第一版做复杂“意图树”。可以先做轻量覆盖层：

1. 从 query 中识别候选概念，来源可以是关键词切分、标题词、索引词表、数学/政治术语表。
2. 搜索仍走同一套高召回 hybrid + AI 精排。
3. 对最终结果按概念做覆盖标记。
4. 页面顶部显示覆盖条：

```text
已覆盖：二项分布、泊松分布
未覆盖：指数分布
```

聚合方式建议：

- 不强行把多个 chunk 合并成一个答案。
- 每个概念至少展示一个代表 chunk，如果召回池中存在。
- 如果同一个 chunk 覆盖多个概念，优先放前。
- 如果存在“总览表/章节总览”chunk，放在概念代表 chunk 之前。

这比纯 TopK 更符合资料库搜索：用户能知道系统找到了哪些、没找到哪些。

## 8. 资料详情抽屉

资料卡点击“详情”后打开右侧抽屉，分四个 tab：

```text
概览
搜索健康
内容预览
高级诊断
```

概览：

- 文件名、学科、资料类型、入库时间。
- 解析质量、chunk 数、索引状态。
- 最近一次搜索命中次数。

搜索健康：

- 可搜索状态。
- 关键词索引状态。
- 向量索引状态，如果启用。
- 最近一次重建索引时间。
- 高频标题/关键词预览。

内容预览：

- `parsed/content.md` 的前几段。
- heading_path 树。
- 代表 chunks。

高级诊断：

- parse_report。
- formula_cleaning。
- llm_cleaning。
- pipeline events。
- 原始 chunks JSON 摘要。

抽屉默认关闭，避免中等宽度屏幕被挤成三栏。关闭抽屉后，用户仍留在当前搜索状态；再次点击“详情”恢复查看。这样可以回答用户之前的疑问：这些报告和 chunks 不是给普通检索体验添负担，而是资料质量和检索问题的“证据层”。

## 9. 状态与错误

空状态：

- 没有资料：引导上传资料。
- 当前学科没有资料：提示切换学科或上传到当前学科。
- 没有强匹配：显示“没有找到强匹配”，不要硬塞弱相关结果。
- 有相关参考但无强匹配：单独展示“相关参考”，并提示换关键词或扩大范围。

错误状态：

- AI 精排额度不足：显示“AI 精排不可用，已回退快速检索”。
- 资料索引缺失：显示“索引未建立”，提供“重建索引”入口。
- 资料质量低：结果卡加提示，不阻塞搜索。

加载状态：

- 快速检索：短 loading。
- AI 精排：显示候选判定进度文案，例如“正在判断候选片段是否适合展示”。

## 10. 后端与数据要求

现有能力已经支持第一版大部分 UI：

- `/api/materials/search` 增加或透出 `mode=hybrid|llm`。
- 结果中使用 `llm_rerank`、`retrieval_plan`、`matched_by`、`score_kind`、`heading_path`。
- 资料列表需要透出 `quality_status`、`overall_confidence`、`chunk_count`、`index_status`。

建议新增或补齐的只读详情能力：

- `GET /api/materials/{material_id}/detail`
- 返回 manifest 摘要、parse_report 摘要、chunks 预览、索引摘要。

建议前端先不展示完整 JSON，只展示摘要；完整 JSON 作为“复制诊断信息”或“查看原始报告”。

## 11. 优先级

P0：搜索体验

- 搜索范围 selector。
- 快速检索 / AI 精排 segmented control。
- 结果卡展示强匹配、相关参考、命中理由、资料来源。
- AI 回退状态显示。
- 多概念覆盖条。

P1：资料健康

- 资料列表显示质量、chunk 数、索引状态。
- 资料详情抽屉。
- 上传完成后的健康摘要。

P2：整理与维护

- 标签、重命名、归档。
- 重建索引。
- 重新解析。
- 批量操作。

## 12. 验收标准

第一版完成后，应能回答这些问题：

- 用户知道当前搜的是哪个范围。
- 用户知道当前是否启用了 AI 精排。
- 搜索“方差公式”时，方差相关结果排在协方差前面，协方差最多作为相关参考。
- 搜索“二项分布 泊松分布”时，页面能显示覆盖了哪些概念。
- 搜索不相关政治/数学交叉问题时，不强行展示当前资料的弱相关内容。
- AI 精排失败时，页面明确显示回退，而不是悄悄装作 AI 已判定。
- 用户能点开资料看到“为什么这份资料可搜索/质量如何”。
- 用户点击“在本资料搜索”时只改变搜索范围，不误打开资料详情。
- 用户点击“详情”时资料详情作为抽屉出现，关闭后不丢失当前搜索状态。
- 普通用户默认不会被 parse_report、chunks JSON 淹没；需要排查时可以找到。

## 13. 自检

本设计没有改动生产代码，没有重构 `qa/`，没有扩大 PDF/MinerU 范围。它复用了现有资料库页面结构和后端检索增强能力，优先解决“用户上传资料后能不能搜准、为什么搜到这些结果”的核心问题。静态 HTML 草图用于评审布局和信息呈现，不作为可直接接入的生产页面。
